# 卡片查看器应用架构与验收矩阵

## 1. 文档定位

本文档记录 `Chips-CardViewer` 项目内部实现边界和任务029迁移后的验收矩阵。公共接口、SDK 契约、箱子运行时和资源打开规范以 `生态共用技术文档/` 为准；本文不定义新的生态公共协议。

## 2. 项目边界

卡片查看器是 `type: app` 应用插件，是 `.card/.box` 查看入口和 Host 托管显示链路的消费方。

正式边界：

- 不解析 `.card/.box` 内部结构；
- 不直接 import 基础卡片插件、箱子布局插件或旧卡片技能实现；
- 不自行拼接复合 iframe、基础卡片 iframe 或箱子布局页面；
- 不硬编码资源处理器应用 ID；
- 不在应用内私建第二套文件入口或命令系统。

应用只通过 `chips-sdk`、`window.chips.*` 正式 Bridge 和组件库 Provider 消费 Host 能力。

## 3. App / Scene / Surface 模型

当前根链路：

- `src/App.tsx`：轻量导出根组件；
- `src/app/AppRoot.tsx`：组合 providers 与 shell；
- `src/app/AppProviders.tsx`：注入 SDK client、`ChipsEnvironmentProvider`、`ChipsThemeProvider`；
- `src/app/AppRuntimeProvider.tsx`：解析 launch context、surface context、打开目标、错误、语言和 trace；
- `src/app/AppShell.tsx`：注册命令处理与快捷入口，并按 scene 渲染内容。

内部 scene：

- `empty`：空启动，显示拖拽和打开文件入口；
- `document-file`：通过本地 `.card/.box` 文件路径进入正式文档窗口；
- `hosted-document`：通过 `launchParams.webDocumentUrl` 承载 Host 已生成的托管文档 URL。

`hosted-document` 是 CardViewer 内部恢复路径，不在本文提升为新的生态公共启动契约。

## 4. `.card/.box` 文件显示链路

`DocumentFileScene` 把文件目标交给 `CardWindow`。`CardWindow` 只调用：

```ts
client.document.window.render({
  filePath,
  locale,
  mode: "view",
});
```

实际分发由 SDK 完成：

- `.card` 分发到 `client.card.compositeWindow.render(...)`；
- `.box` 分发到 `client.box.documentWindow.render(...)`。

事件消费：

- `onReady`：关闭加载态；
- `onError`：显示整张文档 fatal 错误；
- `onNodeError`：记录复合卡片节点降级日志，不把单节点失败升级成整张文档失败；
- `onResourceOpen`：调用 `client.resource.open(...)`，失败时通过 `client.platform.showMessage(...)` 显示可诊断错误。

生命周期：

- 目标变化、主题缓存键变化或组件卸载时，清理 SDK 事件订阅；
- 调用 `FrameRenderResult.dispose()` 释放卡片 render session 或箱子 document window session；
- 从 DOM 移除旧 iframe 后再挂载新 iframe。

## 5. 托管文档承载链路

`HostedDocumentWindow` 用于已经由 Host 提供 `webDocumentUrl` 的场景。该链路直接挂载 `documentUrl` 到 sandbox iframe，并只消费正式运行时消息：

- `chips.composite:ready`
- `chips.box-layout:ready`
- `chips.composite:fatal-error`
- `chips.box-layout:error`
- `chips.composite:resize`
- `chips.composite:resource-open`

sandbox 固定为 `allow-scripts allow-forms`。消息来源允许当前应用 origin、iframe 标记的 `data-chips-origin`，以及 sandbox opaque origin `null`。

高度变化通过 `plugin.surface.resize` 发布，载荷包含 `height`、`contentHeight`、`safeBlockEnd`、`viewportHeight`、`reason` 和 `stable`。

## 6. 命令系统

当前命令定义位于 `src/commands/card-viewer-commands.ts`：

- `commandId`: `com.chips.card-viewer.open-file`
- `handlerId`: `open-file`
- 权限：`platform.read`
- 菜单：`menuId=file`
- 工具栏：`toolbarId=main`

命令 metadata 只包含 i18n key、IconDescriptor、scope、permission 和 placement，不写原始显示文案。应用通过 `createCommandAdapter(client)` 维持 SDK command registry 接入，空态“打开文件”入口仍通过命令调用进入正式处理器；查看态不在页面上渲染 `ChipsMenuBar` 或 `ChipsToolbar`，避免文档内容窗口上方出现应用内菜单栏。

## 7. 主题与 i18n

主题链路：

- Host preload 注入初始主题；
- `AppProviders` 读取文档主题并传给 `ChipsEnvironmentProvider`；
- `RuntimeThemeProvider` 以组件库当前主题或文档主题初始化 `ChipsThemeProvider`；
- `CardWindow` 监听 `useThemeRuntime().cacheKey`，主题变化后重新渲染内容 iframe。

i18n 链路：

- 用户可见文案位于 `i18n/zh-CN.json` 与 `i18n/en-US.json`；
- React 组件通过 `useCardViewerText()` 同步解析文案；
- 根运行时同步 `html[lang]`、`html[dir]` 与 `data-chips-locale`；
- 命令标题、描述、aria、空态、错误态、加载态和 iframe title 均使用 i18n key。

## 8. 验收矩阵

| 范围 | 文件 | 验收点 |
|---|---|---|
| 根组件 | `tests/unit/app.test.tsx` | 空启动、命令打开、`targetPath`、unsupported file、查看态无顶部菜单栏、`webDocumentUrl`、主题刷新、语言同步 |
| 文档窗口 | `tests/e2e/basic-flow.test.tsx` | 真实 `.card/.box` 素材、`document.window.render`、ready/error/node-error/resource-open、cleanup |
| 托管文档 | `tests/unit/hosted-document-window.test.tsx` | sandbox、origin、resize、resource-open 错误诊断 |
| 命令 | `tests/unit/commands.test.ts` | metadata 可序列化、无 raw 文案、菜单/工具栏 placement、manifest 权限 |
| 空态 | `tests/unit/dropzone.test.tsx` | region、aria 描述、错误播报、`.card/.box` 文件标记 |
| 主题与 a11y | `tests/unit/theme-a11y.test.ts` | 文档 surface 使用主题 token，加载态和错误态语义角色 |
| 真实素材路径 | `tests/fixtures/real-documents.ts` | ProductFinishedProductTestingSpace 中的真实卡片与箱子样本 |

正式验证命令：

```bash
npm run lint
npm test
npm run build
npm run validate
```

## 9. 任务029闭环边界

任务029闭环后，CardViewer 已完成以下范围：

- `.card/.box` 文件入口对齐 `manifest.yaml` 与 SDK 文档窗口；
- App/Scene/Surface 结构对齐应用插件 vNext 基线；
- 命令、主题、i18n、资源打开和可访问性接入正式链路；
- 真实素材回归覆盖卡片、箱子和复合卡片事件协议。

未实现的产品能力不在当前文档中承诺。后续若要新增最近打开、导出、诊断面板、阅读模式或更多查看工具，应在对应新任务中先核对公共契约与现有代码，再补充项目文档或生态共用技术文档。
