# 生产域名与对象存储部署说明

## 文档定位

- 本文档说明 `Chips-CommunityPlatformServer` 在生产环境绑定正式域名、HTTPS 与外部 S3 兼容对象存储的部署口径；
- 本文档以当前代码中的 `deploy/docker-compose.yml`、`deploy/nginx/nginx.conf`、`packages/server/src/config/env.ts`、`packages/server/src/storage/s3.ts` 为准；
- 本文档只记录社区服务器自身部署细节，不替代对象存储厂商控制台、DNS 控制台或证书平台的操作文档。

## 1. 域名入口

生产环境推荐使用单一主访问域名作为 `BASE_URL`，另一个域名只做跳转。

当前 `nginx.conf` 的正式口径为：

- `http://chipscard.space` -> `https://www.chipscard.space`
- `http://www.chipscard.space` -> `https://www.chipscard.space`
- `https://chipscard.space` -> `https://www.chipscard.space`
- `https://www.chipscard.space` 承载社区前台、后台与 API
- `https://file.chipscard.space` 承载对象存储公开资源

正式环境的 `BASE_URL` 必须与主访问域名完全一致：

```env
BASE_URL=https://www.chipscard.space
```

原因：

- 服务端生产 CORS 只允许 `BASE_URL` 同源请求；
- refresh token Cookie 在生产环境启用 `Secure`；
- 前台 `/api` 与 `/admin/api` 都按同源路径访问。

## 2. HTTPS 证书

当前 Nginx 容器从以下路径读取证书：

```text
Chips-CommunityPlatformServer/deploy/certs/chipscard.space_ca.crt
Chips-CommunityPlatformServer/deploy/certs/chipscard.space.key
```

证书必须覆盖：

- `chipscard.space`
- `www.chipscard.space`

证书私钥不进入 Git，`deploy/certs/*` 已由项目 `.gitignore` 排除。

## 3. 对象存储写入入口

服务端通过 S3 兼容协议写入对象存储。Docker 全栈模式下，容器内 `S3_ENDPOINT` 来自：

```yaml
S3_ENDPOINT: ${S3_RUNTIME_ENDPOINT:-http://minio:9000}
```

因此生产外部对象存储应在 `deploy/.env` 中配置：

```env
S3_RUNTIME_ENDPOINT=https://s3.ap-southeast-1.qiniucs.com
S3_ENDPOINT=https://s3.ap-southeast-1.qiniucs.com
S3_REGION=ap-southeast-1
S3_FORCE_PATH_STYLE=true
```

`S3_ENDPOINT` 保留给本地 Node 进程直接读取；`S3_RUNTIME_ENDPOINT` 保证 Docker 容器运行时也使用同一生产入口。

七牛云 S3 兼容写入必须使用与公开直连资源兼容的校验配置：

```ts
requestChecksumCalculation: 'WHEN_REQUIRED'
responseChecksumValidation: 'WHEN_REQUIRED'
```

原因：

- AWS SDK v3 在默认配置下会对 `fs.createReadStream(...)` 上传启用流式校验编码；
- 七牛云 S3 兼容接口会把这类请求里的 `content-encoding: aws-chunked` 持久化为对象元数据；
- 浏览器通过 `file.chipscard.space` 直连对象时可能误按 `aws-chunked` 解码，表现为新上传 HTML 或图片乱码、图片查看器无法正常显示；
- 当前代码在 `packages/server/src/storage/s3.ts` 的 `getS3Client()` 中统一设置上述配置，上传仍保持流式读取，不需要把大文件整体读入内存。

部署验证时，任意新上传的图片、HTML、CSS、JS 等公开对象响应头都不应再包含：

```text
content-encoding: aws-chunked
```

文本类资源应携带明确 charset，例如：

```text
content-type: text/html; charset=utf-8
```

## 4. 单物理 Bucket 映射

社区服务器业务上仍保留四类逻辑 bucket：

- `chips-card-resources`
- `chips-card-html`
- `chips-avatars`
- `chips-covers`

当对象存储服务商只使用一个物理 bucket 时，设置：

```env
S3_BUCKET_NAME=chipscardspace
```

写入规则：

```text
逻辑 bucket: chips-card-html
业务 key: user-1/card-1/index.html
物理 bucket: chipscardspace
物理 key: chips-card-html/user-1/card-1/index.html
公开 URL: https://file.chipscard.space/chips-card-html/user-1/card-1/index.html
```

这样可以保持数据库中的 `coverUrl`、`htmlUrl` 和前端资源路径稳定，同时满足单 bucket 部署要求。

## 5. 公开资源入口

生产环境推荐使用对象存储服务商绑定的自定义 HTTPS 域名：

```env
S3_PUBLIC_URL=https://file.chipscard.space
```

七牛云侧需要保证该域名已绑定到空间或 CDN，并配置有效 HTTPS 证书。当前正式资源域名为：

```text
https://file.chipscard.space/
```

说明：

- 浏览器直接访问 `https://file.chipscard.space/...`，社区主站不承担资源代理流量；
- 对象实际写入七牛云单物理 bucket `chipscardspace`，公开路径仍带逻辑 bucket 前缀；
- Nginx 保留 `/cdn/` 到 `https://file.chipscard.space/` 的 301 跳转，用于把旧入口统一到正式资源域名。

## 6. 部署验证

部署后至少验证：

```bash
curl -k --resolve www.chipscard.space:443:111.92.241.17 https://www.chipscard.space/api/v1/health
curl -k --resolve www.chipscard.space:443:111.92.241.17 -I https://www.chipscard.space/
curl -k --resolve www.chipscard.space:443:111.92.241.17 -I https://www.chipscard.space/admin/
```

若 DNS 已正式解析到服务器，可去掉 `--resolve`。

资源链路验证以新上传内容为准，检查返回的 `htmlUrl` / `coverUrl` 是否形如：

```text
https://file.chipscard.space/chips-card-html/...
https://file.chipscard.space/chips-covers/...
```

## 7. 生产端口边界

生产 Compose 默认只映射：

- `80`
- `443`

以下服务只在 Docker 网络内访问，不直接暴露公网端口：

- PostgreSQL `5432`
- Redis `6379`
- MinIO `9000 / 9001`

外部对象存储部署下，MinIO 服务仅作为本地开发/回退组件保留，不属于生产资源写入链路。
