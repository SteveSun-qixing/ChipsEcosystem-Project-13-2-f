# 文件转换编排模块技术方案

## 1. 当前仓库基线

本仓已由 `chips-scaffold-module` 初始化，具备：

- `manifest.yaml`
- `contracts/`
- `src/`
- `tests/`

当前仓库已完成正式文件转换编排能力替换，代码实现与本文档保持一致。

## 2. 目标结构

本仓内部实现建议分为：

- `request-normalizer`
- `pipeline-planner`
- `step-executor`
- `job-progress-aggregator`
- `result-normalizer`

## 3. 流水线规划规则

- `card -> html`：单步
- `card -> pdf`：两步
- `card -> image`：两步
- `html -> pdf/image`：单步

流水线规划本身不依赖具体 provider 仓库，只依赖正式 capability 名称。

## 4. 原子模块调用方式

编排模块调用原子模块时，必须使用 Host 注入的 `ctx.module.invoke(...)`：

- 不直接 import 原子模块代码
- 不复制原子模块 schema
- 不复写原子模块内部输出逻辑

当前下游正式能力基线：

- `converter.card.to-html` 负责把 `themeId / locale` 透传到 Host `card.render`
- `converter.html.to-pdf` 负责调用 Host `platform.renderHtmlToPdf`
- `converter.html.to-image` 负责调用 Host `platform.renderHtmlToImage`
- 编排模块组装子模块 `input` 时，只允许下发“已定义”的可选字段；未提供的 `options.*` 字段必须省略，避免触发下游 schema 校验失败

## 5. 中间产物治理

`pdf/image` 链路中的 HTML 中间产物必须被视为临时目录：

- 由编排模块统一创建
- 强制使用 `packageMode = "directory"`
- 强制使用 `includeAssets = true`
- 强制使用 `includeManifest = true`
- 文件与目录治理通过 Host 注入的 `ctx.host.invoke("file.*", payload)` 正式动作完成
- 临时根目录放在最终输出文件同级目录下，避免依赖 Node 内建路径模块导致构建产物漂移
- 由编排模块统一传递给下游步骤
- 成功或失败后统一清理

最终交付物也必须走事务式发布：

- 原子模块实际输出先落到同级 `.chips-file-conversion-*` 临时根目录下的 `final/` 子目录；
- `artifacts[].path` 和 `outputPath` 始终返回调用方请求的最终交付路径，不暴露 staging 路径；
- 若 `output.overwrite = true` 且旧输出已存在，提交阶段先把旧输出移动到临时 `backup/` 子目录，再把新输出移动到 `output.path`；
- 如果提交新输出失败，模块必须尝试把 `backup/` 中的旧输出移动回 `output.path`，并返回 `CONVERTER_OUTPUT_COMMIT_FAILED`；
- 如果任一步骤失败、取消或下游 provider 缺失，模块不得提前删除旧输出，只清理本轮临时根目录。

## 6. 错误语义

编排层只归一与“编排”直接相关的错误，不覆盖原子模块已经返回的 `CONVERTER_*` 业务错误：

- `MODULE_PROVIDER_NOT_FOUND` -> `CONVERTER_PIPELINE_PROVIDER_MISSING`
- `MODULE_CAPABILITY_NOT_DECLARED` / `PERMISSION_DENIED` / `SERVICE_PERMISSION_DENIED` -> `CONVERTER_PIPELINE_PERMISSION_DENIED`
- 无法提交最终输出 -> `CONVERTER_OUTPUT_COMMIT_FAILED`

归一后的错误必须在 `details` 中保留下游 capability、method 以及 Host 原始错误对象，方便 SDK、CLI 和审计日志继续定位。

- 结果归一测试
