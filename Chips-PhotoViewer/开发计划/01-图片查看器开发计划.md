# 图片查看器开发计划

## 1. 计划目标

本计划用于记录 `Chips-PhotoViewer` 首版的实施顺序、当前完成情况与后续扩展边界。

## 2. 阶段状态

### 阶段一：项目基线冻结

状态：已完成

已交付：

1. 使用官方应用插件脚手架初始化项目；
2. 清理脚手架身份残留；
3. 冻结需求文档、技术文档、开发计划；
4. 建立图片查看器相关生态工单与项目记录。

### 阶段二：图片打开与查看基线

状态：已完成

已交付：

1. `launchParams.targetPath` 启动恢复；
2. 应用内手动选择图片文件；
3. 单图查看态；
4. 空态、加载态、错误态；
5. 路径、分辨率、缩放比例、文件大小信息区。

### 阶段三：缩放与保存

状态：已完成

已交付：

1. 放大；
2. 缩小；
3. 适应窗口；
4. 实际大小；
5. 保存图片副本。

### 阶段四：Host 接入联调

状态：已完成

已交付：

1. Host 通用 `file-handler:<ext>` 文件关联分发；
2. Host 启动入口对普通扩展名文件的接收；
3. 安装器根据内置 app 插件能力条件注册图片类型；
4. 图片查看器作为可选内置插件接入 Host 分发链路；
5. “没安装插件就不接图片”的发行级行为收口。

### 阶段五：后续生态扩展

状态：后续规划

后续仅在共享契约冻结后再进入：

1. 非文件路径图片资源转交；
2. 多处理器优先级治理；
3. 动态卸载 / 回收系统文件关联治理。

### 阶段六：应用框架 vNext 迁移

状态：已完成

已交付：

1. `src/App.tsx` 收敛为轻量 re-export，真实入口迁入 `src/app/AppRoot.tsx`；
2. 接入 `ChipsEnvironmentProvider`、`ChipsThemeProvider`、surface launch context、权限和诊断回调；
3. 新增 `AppRuntimeProvider` 统一管理图片目标、资源解析、保存、反馈、语言和平台环境；
4. 新增 scene registry，冻结空启动与图片查看两个 scene；
5. 保持 `targetPath`、`resourceOpen`、`chips.book-card` 图片序列、手动打开、拖拽打开、缩放平移和保存语义不变。

### 阶段七：命令系统与组件库壳层迁移

状态：已完成

已交付：

1. 新增 `src/commands/photo-viewer-commands.ts` 和 `usePhotoViewerCommands.ts`；
2. 打开、保存、上一张、下一张、放大、缩小、适应窗口、实际大小全部注册为 Host command；
3. 底部浮动 dock 改为组件库 `ChipsMenuBar` 和 `ChipsToolbar` 消费命令；
4. 命令文案全部使用 i18n key，图标使用 `IconDescriptor`；
5. 命令状态随图片加载、保存中和图片序列边界动态更新。

### 阶段八：主题、i18n、A11y 与验证收口

状态：已完成

已交付：

1. 命令、菜单、工具栏、状态、错误和视口可访问名称补齐中英文多语言资源；
2. CSS 改为使用主题 token fallback，移除旧私有 toolbar button 视觉体系；
3. 图片视口、空态和反馈补齐基础可访问语义；
4. 新增命令 metadata 和状态派生单元测试；
5. 完成正式脚本验证。

## 3. 当前交付清单

截至 2026-05-26，当前已交付：

1. 图片查看器正式应用插件；
2. Host 泛化文件关联接线；
3. 安装器能力驱动的图片文件关联注册；
4. 项目文档、Host 文档、工单记录同步更新；
5. AppRuntime / Scene / Environment vNext 运行时入口；
6. Host command registry 与组件库命令消费壳层；
7. 主题 token、i18n、A11y 基础收口；
8. 与改动范围匹配的单元测试、集成测试、契约测试和正式脚本验证。

## 4. 验证计划与结果

2026-05-26 本轮已实际执行并通过：

1. `Chips-PhotoViewer`
   - `npm run lint`
   - `npm test`，5 个测试文件、17 个测试用例通过
   - `npm run build`
   - `npm run validate`

本轮未修改 `Chips-Host`，因此未重复执行 Host 验证脚本。

## 5. 收口结论

图片查看器首版已经完成当前产品范围内的正式交付，并已迁移到应用框架 vNext 基线。

后续如需继续扩展，优先顺序应为：

1. 共享资源转交契约；
2. 默认处理器治理；
3. 安装器 / 卸载器回收策略。
