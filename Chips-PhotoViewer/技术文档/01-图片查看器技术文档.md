# 图片查看器技术文档

## 1. 文档边界

本文只描述 `Chips-PhotoViewer` 本仓内部实现与当前已落地的 Host / SDK 接线事实。涉及未来生态通用资源票据、默认处理器治理等公共契约，不在本文件中重新定义。

## 2. 当前正式外部链路

### 2.1 Host 资源打开入口

当前 Host 已新增正式 `resource.open` 路由，图片查看器可以通过两类能力参与该路由：

1. `resource-handler:view:image/*`
2. `file-handler:.png/.jpg/...`

Host 当前处理顺序如下：

1. 优先匹配 `resource-handler:view:image/*` 这一类 MIME 处理器；
2. 若未命中，再回退到 `file-handler:<ext>`；
3. 命中后统一通过 `plugin.launch(...)` 启动图片查看器；
4. 启动上下文中注入 `launchParams.resourceOpen`，并在可解析真实文件路径时继续补充 `targetPath`。

这意味着：

1. 卡片查看器、箱子查看器、未来的媒体容器都不需要硬编码图片查看器插件 ID；
2. 只要调用正式 `resource.open`，Host 就会自动寻找图片处理器。

### 2.2 Host 文件关联入口

当前 Host 已经完成两层接线：

1. `Chips-Host/src/main/electron/app-entry.ts`
   - 进程参数、macOS `open-file`、`second-instance` 现在会接收任意带扩展名的文件路径；
2. `Chips-Host/src/main/core/file-association.ts`
   - `.card` 继续走卡片链路；
   - `.box` 继续走箱子链路；
   - 其它扩展名会查询 `plugin.query({ type: "app", capability: "file-handler:<ext>" })`；
   - 命中后调用 `plugin.launch(...)`，把 `targetPath` 交给目标应用插件。

因此，图片查看器只要声明 `file-handler:.png/.jpg/...`，就能通过正式 Host 文件关联链路接收图片文件。

### 2.3 安装器条件注册

`Chips-Host/src/main/installer/macos-installer.ts` 现在会：

1. 扫描内置 app 插件 manifest 中的 `file-handler:<ext>`；
2. 推导要写入 `Info.plist` 的文档类型；
3. 只为真正随包携带的内置插件注册对应文件类型。

这意味着：

1. 标准 Host 发行包如果携带 `Chips-PhotoViewer`，会注册图片类型；
2. 如果发行包不携带图片查看器，安装器不会注册这些图片类型；
3. Host 运行时也会把缺失的图片查看器视为可选内置插件，不会因为缺 bundle 而启动失败。

### 2.4 SDK / Bridge 能力

图片查看器当前使用的正式能力：

1. `client.platform.getLaunchContext()`：读取 `trigger`、`targetPath` 与 `launchParams.resourceOpen`
2. `launchParams.resourceOpen`：读取由 Host 资源路由注入的资源上下文
3. `client.platform.openFile(...)`：手动选择图片
4. `client.platform.saveFile(...)`：选择保存位置
5. `client.file.copy(...)`：保存具有真实本地路径的图片副本
6. `client.resource.resolve(...)`：将本地路径、远端 URL 或 Web 本地文件 token 转换为可直接显示的资源 URI
7. `client.resource.readBinary(...)`：保存 Host 托管资源图片时读取当前图片原始字节
8. `client.file.write(...)`：把 Host 托管图片字节写入用户选择的保存路径
9. `client.command.register/unregister/list/invoke/setState/onInvoked(...)`：注册并消费图片查看器命令
10. `client.theme.getCurrent()` / `theme.changed`
11. `client.i18n.getCurrent()` / `language.changed`

## 3. 应用内部架构

### 3.1 AppRuntime / Environment / Scene

当前项目已经迁移到应用脚手架 vNext 心智：

1. `src/App.tsx`
   - 只作为轻量 re-export；
   - 真实根组件为 `src/app/AppRoot.tsx`。
2. `src/app/AppProviders.tsx`
   - 接入 `ChipsEnvironmentProvider`；
   - 注入 `chips-sdk` client、初始主题、初始语言、launch context、surface context、权限和诊断回调；
   - 再通过 `ChipsThemeProvider` 接收 Host 主题变化。
3. `src/app/AppRuntimeProvider.tsx`
   - 集中维护图片目标、当前索引、资源解析、保存、反馈、语言、平台和 surface 环境；
   - 只通过 `chips-sdk` 正式接口访问 Host 能力。
4. `src/app/AppShell.tsx`
   - 组合 `ChipsCommandProvider` 与 `PhotoViewerStage`；
   - 只负责 scene 壳层和命令消费组合，不直接实现 Host 能力。
5. `src/app/scene-registry.ts`
   - 当前定义空启动和图片查看两个 scene；
   - scene 只表达应用状态，不改变产品交互逻辑。
6. `src/runtime/*`
   - `chips-client.ts` 单例创建 SDK client；
   - `launch-context.ts` 归一 Host surface launch context；
   - `environment-client.ts` 适配组件库 Environment client；
   - `theme-runtime.ts` 读取文档注入主题快照。

### 3.2 Launch Intake

打开入口当前统一归一为 `LaunchImageTarget`：

1. 普通图片打开：优先从 `launchParams.resourceOpen.filePath` 建立单项图片队列，再回退到 `launchParams.targetPath`，最后回退到 `resourceOpen.resourceId`；
2. 电子书图片包打开：当 `resourceOpen.payload.kind = "chips.book-card"` 且 `mode = "image-sequence"` 时，从 `payload.resources.images[]` 建立有序图片队列；若 payload 内资源仍是卡片根目录相对路径，则以顶层 `resourceOpen.resourceId/filePath` 命中的当前图片推导同一资源基准，恢复图片序列的可读资源标识；
3. 文件对话框返回的本地路径建立单项图片队列。

入口层只做三件事：

1. 归一启动参数中的本地路径、Host 托管资源 URL 或电子书图片包资源描述；
2. 校验图片文件名、相对路径或资源标识是否在支持格式内；
3. 把图片队列交给后续图片会话层。

当前真实素材回归覆盖 `ProductFinishedProductTestingSpace/图片.jpg` 的 `resource-open-service` 启动参数，以及 `电子书图片.zip` 解包后的有序图片目录通过 `chips.book-card` / `mode: "image-sequence"` payload 进入图片队列的链路。测试从当前工作区根目录解析测试空间，不写死历史工作区绝对路径。

### 3.3 Image Session

应用内部会话状态由以下信息组成：

```ts
interface ImageSource {
  sourceId: string;
  filePath?: string;
  fileName: string;
  resourceUri: string;
  revision: number;
}
```

以及以下派生状态：

1. `isResolving`
2. `isImageLoaded`
3. `feedback`
4. `imageDimensions`
5. `camera`
6. `imageTarget`
7. `currentImageIndex`

其中：

1. `sourceId` 是当前图片的正式读取标识，可能是本地路径、Host 托管资源 URL 或上游 payload 中的 `resourceId`；
2. `filePath` 只在 Host 能解析真实本地路径或用户手动打开本地文件时存在；
3. `resourceUri` 来自 `resource.resolve(...)`；
4. `revision` 用于在重复打开同一路径时强制刷新图片元素；
5. `imageTarget.images` 保存图包或单图队列，`currentImageIndex` 表示当前显示项。

其中 `camera` 统一收口图片查看态的瞬时交互状态：

```ts
interface ViewerCameraState {
  zoomMode: "fit" | "manual";
  manualScale: number;
  viewportSize: ViewportSize | null;
  panOffset: { x: number; y: number };
}
```

当前正式实现已经把这部分逻辑从应用入口拆到独立 `usePhotoViewerCamera(...)` Hook 中，避免文件接入、主题/多语言、图片手势和布局骨架继续混在一个大组件里。

### 3.4 缩放模型

缩放逻辑抽到 `src/utils/image-viewer.ts`，核心规则如下：

1. `fit` 模式根据图片原始尺寸和“稳定视口窗口”尺寸实时计算 `fitScale`
2. `manual` 模式维护独立的 `manualScale`
3. 放大 / 缩小以固定倍率 `1.25` 递进
4. 缩放范围统一钳制在 `0.1 ~ 8`
5. `fitScale` 采用当前查看器首版稳定规则：横图优先按视口宽度适配，竖图优先按视口高度适配，方图取宽高两者中的更小值。

### 3.5 跨输入方式交互

视口交互当前统一由 `Wheel + Pointer Events` 驱动：

1. 鼠标滚轮
   - 直接作为缩放输入；
2. 触摸板
   - 普通双指滚动继续交给视口原生滚动；
   - `ctrl/meta + wheel` 等价于捏合缩放；
3. 鼠标 / 触控笔 / 触摸屏
   - 单指或主按键拖动画面平移；
4. 触摸屏双指
   - 通过 Pointer Events 计算两点距离与中点，执行锚点缩放。

补充规则：

1. 未带修饰键的 `wheel` 事件会根据增量形态区分“鼠标滚轮缩放”与“触控板滚动平移”；
2. 图片平移不再依赖滚动容器，而是维护独立 `panOffset`，因此任何缩放倍率下都允许直接拖动；
3. 缩放时会基于当前指针锚点重新投影 `panOffset`，尽量保持用户正在观察的区域不跳变；
4. 新图片打开、切回 `fit` 模式或切到实际大小时，会把平移偏移归零，保证默认打开位置稳定。

### 3.6 Commands 与查看层布局

图片查看器命令已收口到 `src/commands/`：

1. `photo-viewer-commands.ts`
   - 定义稳定 command id、handlerId、i18n key、IconDescriptor、scope、权限、菜单/工具栏 placement、快捷键和状态；
   - 禁止原始 `title/description/ariaLabel/label` 文案字段；
   - 根据当前图片加载状态、保存状态和图片序列边界派生 command enabled/disabled 状态。
2. `usePhotoViewerCommands.ts`
   - 通过 `createCommandAdapter(client)` 接入组件库命令消费；
   - 在应用启动时注册命令，在卸载时注销命令；
   - 监听 `command.invoked`，再由本地 handler 执行打开、保存、上一张、下一张、放大、缩小、适应窗口和实际大小。
3. `PhotoViewerStage`
   - 继续负责图片视口、拖拽、滚轮、指针、图片加载和图片相机交互；
   - 底部浮动 dock 由菜单区、图标工具栏区和状态区三段组成；
   - 菜单继续使用 `ChipsMenuBar` 消费命令视图，图标工具栏通过 `resolveCommandToolbarItems(...) + ChipsIconButton` 消费同一份命令视图并按 `file / sequence / zoom` 分组；
   - 注册到 Host 的命令定义保留 `shortcut`，但传入查看器菜单和工具栏的展示视图会移除 `shortcut` 字段，因此界面按钮与菜单项不再显示右侧快捷键文本；
   - 命令事件到达后调用现有 runtime handler 或 camera 方法，不新建第二套动作事实来源。

当前查看层已经拆成三层稳定结构：

1. `PhotoViewerStage`
   - 作为唯一的全窗口舞台根节点；
2. `photo-viewer-frame`
   - 作为稳定的图片显示窗口，始终铺满整个应用窗口；
3. `photo-viewer-chrome`
   - 单独承载底部 dock 与反馈浮层，不参与图片布局，也不受图片缩放影响。

其中：

1. 图片本体始终渲染在 `photo-viewer-image-frame` 中，并围绕视口中心做缩放与平移；
2. 底部居中的浮动 dock 固定挂在 `photo-viewer-chrome` 上，菜单弹层向上展开，工具按钮使用稳定 36px 图标按钮轨道避免快捷键文本挤压布局；
3. 状态反馈仅在保存成功、打开失败等需要提示时短时出现，不默认展示图片信息面板。

### 3.7 保存链路

保存不读取图片二进制后重写，而是直接走正式文件复制链路：

1. `platform.saveFile(...)` 获取目标路径；
2. 若用户取消，直接结束；
3. 若目标路径等于源路径，返回提示；
4. 如果当前图片有真实本地路径，调用 `file.copy(sourcePath, destPath)`；
5. 如果当前图片来自 Host 托管资源且没有真实本地路径，调用 `resource.readBinary(sourceId)` 后通过 `file.write(destPath, bytes, { encoding: "binary" })` 保存原始字节。

这样可以保证首版“保存图片”语义稳定为“保留原始内容的副本输出”。

### 3.8 主题、多语言与 A11y

应用壳层通过以下方式接入生态：

1. `ChipsThemeProvider` 负责主题运行时同步；
2. 首屏先读取文档注入的主题快照，减少闪烁；
3. 文案统一来自 `i18n/zh-CN.json` 与 `i18n/en-US.json`；
4. 通过 `language.changed` 跟随 Host 当前语言变化。
5. 用户可见命令标题、描述、aria label、菜单标题、工具栏标题、状态和错误反馈全部使用多语言 key；
6. 图片视口使用具名 `role="group"`，空态按钮可聚焦，反馈使用 `status/alert` 与 `aria-live`；
7. 应用 CSS 使用主题 token fallback 和组件库命令消费组件公开结构，不再维护私有基础按钮视觉体系。

## 4. Manifest 与能力声明

当前 `manifest.yaml` 关键声明如下：

### 4.1 `capabilities`

```yaml
capabilities:
  - resource-handler:view:image/*
  - file-handler:.png
  - file-handler:.jpg
  - file-handler:.jpeg
  - file-handler:.webp
  - file-handler:.gif
  - file-handler:.bmp
  - file-handler:.svg
  - file-handler:.avif
```

### 4.2 `permissions`

```yaml
permissions:
  - resource.read
  - file.read
  - file.write
  - platform.read
  - theme.read
  - i18n.read
  - command.read
  - command.write
  - command.invoke
```

这些权限分别对应：

1. 解析图片资源 URL；
2. 读取 Host 托管资源或文件元信息；
3. 保存图片副本；
4. 打开/保存系统对话框；
5. 主题读取；
6. 当前语言读取；
7. 命令注册、查询、调用和状态更新。

## 5. “没安装插件时 Host 不接图片”的实现方式

当前正式行为如下：

1. `Chips-PhotoViewer` 被设计为 Host 的可选内置 app 插件；
2. 只有当发行包真正携带该插件时，安装器才会根据它的 `file-handler:<ext>` 能力写入图片文件关联；
3. 若发行包不带该插件：
   - 安装器不会注册图片类型；
   - Host 启动时也不会因为缺少图片查看器 bundle 而报错；
   - 结果就是 Host 不会接住这些图片文件。

当前尚未处理的边界是：

1. 如果用户已经安装过带图片查看器的 Host，再通过其它方式移除插件，操作系统已有的文件关联回收仍需要依赖安装器 / 卸载链路治理；
2. 这不影响“未安装图片查看器插件时，Host 不注册也不接图片”的首版结论。

## 6. 卡片查看器点击图片的正式闭环

当前已经正式闭环的链路如下：

1. 图片基础卡片点击图片后，只表达 `openResource(...)` 意图；
2. Host 复合卡片运行时把该意图转发给卡片查看器；
3. 卡片查看器调用 `client.resource.open(...)`；
4. Host 自动匹配图片查看器的 `resource-handler:view:image/*`；
5. 图片查看器通过 `launchParams.resourceOpen.filePath` 或 `targetPath` 恢复查看状态。

## 7. 当前剩余边界

本轮仍未扩展：

1. 纯内存二进制资源、不落地文件路径时的专用查看器载荷协议；
2. 多个图片查看器并存时的默认处理器优先级治理。
3. TIFF 转 PNG、缩略图、颜色提取等底层图片能力不在应用层复制；后续如产品需要入口，必须通过 Host `resource.convertTiffToPng` 或模块 `image.color.pick` 正式能力接入。

这两项属于后续生态扩展，不是当前图片查看器首版阻塞。
