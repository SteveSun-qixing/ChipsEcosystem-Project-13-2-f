# 前置架构决议清单

## 1. 必须先回答的问题

在继续任务002之前，至少需要先完成以下正式决议。

### 1.1 编辑态运行时归属

- 编辑态非 iframe 复合卡片运行时，是否仍归属 Host L9 统一渲染层？
- 还是允许 `Chips-EditingEngine` 成为生态中的特殊应用层运行时？

### 1.2 Host 对外契约

- Host 是否需要新增正式动作，例如：
  - 返回可组合节点树；
  - 返回编辑态场景树；
  - 返回可直接挂载的节点运行时描述；
- 如果新增，现有 `card.render` / `card.renderEditor` 与新接口之间如何分工？

### 1.3 基础卡片插件契约

- 当前插件只有 `renderBasecardView` 与 `renderBasecardEditor`。
- 是否需要新增第三类导出，例如编辑态渲染导出？
- 若新增，生命周期、输入输出、数据更新、销毁清理、错误模型如何定义？

### 1.4 主题与多语言链路

- 编辑态节点是继续由 Host 注入主题和 i18n，还是交给应用层注入？
- 组件 token、主题作用域链、语言切换事件如何在新链路中保持一致？

### 1.5 交互与数据协议

- 节点选中、拖拽、插入指示、尺寸变化、命中测试、外层滚动代理如何定义？
- 应用层与节点层的数据操作边界如何划分？
- 编辑态节点是否允许直接读写卡片内容，还是仍通过 Host 服务动作完成？

### 1.6 质量门禁

- 需要哪些仓库同步改造：
  - `Chips-Host`
  - `Chips-SDK`
  - `Chips-EditingEngine`
  - 基础卡片插件模板与既有插件
  - 生态共用技术文档
  - 生态设计原稿
- 契约测试、a11y、性能基线、E2E 和验收文档如何一起补齐？

## 2. 未决前禁止推进的事项

在上述问题没有形成正式决议前，不应推进以下事项：

- 在编辑引擎仓内直接自建基础卡片渲染运行时；
- 直接 import 基础卡片插件渲染源码作为正式方案；
- 为了绕开正式链路而私接主题或 i18n 上下文；
- 在应用层另外定义一套节点事件协议；
- 先写实现、后补文档和契约。

## 3. 建议的后续流程

建议下一步先由架构负责人组织一次正式决议，输出以下产物后，再重新开启任务002：

1. 一份新的架构决议文档，明确编辑态运行时归属与正式方案方向。
2. 一份跨仓改造范围清单，明确需要改哪些仓库、哪些契约和哪些测试。
3. 一份更新后的生态共用技术文档口径，避免编辑引擎与 Host/SDK 各说各话。

在这些前置产物形成之前，任务002保持阻塞。
