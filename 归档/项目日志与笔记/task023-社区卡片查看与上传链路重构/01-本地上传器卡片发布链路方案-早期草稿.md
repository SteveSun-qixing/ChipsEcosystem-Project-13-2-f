# 本地上传器卡片发布链路方案（早期草稿归档）

## 归档说明

本文是 task023 早期围绕“官方本地上传器处理 `.card` 后提交社区服务器”的方案草稿。

当前任务已扩大为“社区卡片查看与上传链路整体重构”，并明确所有主链路都直接转发和查看 `.card` 文件，不再把 HTML 转换作为上传或查看前置。因此本文归档保留，后续以同目录中的以下文档为准：

- `../00-任务文档索引.md`
- `../01-总体重构方案.md`
- `../02-接口与数据模型方案.md`
- `../03-实施步骤与验收清单.md`

## 早期背景

当前社区服务器已经提供网页端上传接口：

- `POST /api/v1/upload/card`
- `POST /api/v1/upload/box`

本地工具可以登录后复用这些接口上传，但当前卡片上传链路会把完整 `.card` 发送到社区服务器，再由社区服务器执行资源上传、URL 替换、重新打包、HTML 转换、封面 HTML 导出和数据库状态更新。

早期目标是让官方本地上传器承担卡片资源发布预处理，降低社区服务器上传带宽和处理压力。

## 早期目标口径

官方本地上传器处理 `.card` 的早期目标：

1. 用户在本地上传器登录社区账号；
2. 上传器向社区服务器申请上传 / 发布会话；
3. 上传器在本机解包 `.card`；
4. 上传器把卡片内部资源上传到资源服务器；
5. 上传器将 `.card` 内部资源引用替换为资源服务器 URL；
6. 上传器重新打包处理后的 `.card`；
7. 上传器把处理后的 `.card` 发送给社区服务器；
8. 社区服务器完成鉴权、配额、结构校验、对象归属校验、保存和数据库登记。

边界：

- 本地上传器阶段不做 HTML / 封面 HTML 转换；
- 如果后续搜索索引、静态预览、旧入口兼容或其他服务端能力需要转换，由社区服务器在需要时转换；
- 不能把对象存储长期密钥写入本地上传器；
- 不能绕过社区服务器登记，直接把资源写进对象存储后视为发布完成。

## 早期代码现状记录

### 登录与鉴权

`Chips-CommunityPlatformServer/packages/server/src/routes/auth.ts` 中：

- `POST /api/v1/auth/login` 返回 `accessToken`；
- 受保护接口使用 `Authorization: Bearer <accessToken>`。

这说明本地上传器可以作为 HTTP 客户端登录并调用社区 API。

### 当前上传入口

`Chips-CommunityPlatformServer/packages/server/src/routes/upload.ts` 中：

- `/api/v1/upload/card` 读取 multipart `file`；
- 服务端检查 `.card` 扩展名和大小；
- 服务端将上传流写入临时文件；
- 服务端创建卡片数据库记录；
- 服务端异步调用卡片处理 pipeline。

### 当前服务端卡片流水线

服务端卡片流水线当前执行：

1. 解包 `.card`；
2. 处理 file-backed richtext Markdown；
3. 上传卡片资源到对象存储；
4. 替换 content / cover 中的资源 URL；
5. 删除原始本地资源并重新打包 `.card`；
6. 调用 Host 转换插件输出 HTML；
7. 输出封面 HTML；
8. 上传内容 HTML 和封面 HTML；
9. 更新数据库状态。

早期方案认为，本地上传器目标会把第 1 到第 5 步前移到用户设备；第 6 到第 8 步不在本地上传器阶段执行。

### 当前对象存储写入

对象存储写入使用服务端 S3 客户端和服务端环境变量：

- `S3_ACCESS_KEY`
- `S3_SECRET_KEY`
- `S3_ENDPOINT`
- `S3_PUBLIC_URL`

早期方案指出，当时没有面向本地上传器的预签名 URL、短期凭证、上传会话或资源清单确认接口。

## 早期查看链路判断

早期进一步确认：如果 Web 端 CardViewer 可以直接消费 `.card`，就可以省掉发布时转 HTML 这条链路。

当时核对到：

- 社区卡片详情页仍依赖 `htmlUrl`；
- CardViewer 有 `remote-card-file` 类型，但会被解析为 unsupported；
- 本地 `.card` 查看依赖 Host 本地文件路径渲染，不等价于网页远程 `.card` URL 渲染。

因此早期结论是：目标可以设计为“网页端 CardViewer 直接查看 `.card` 文件”，但需要补齐 Web CardViewer / 社区 Host Runtime 的远程 `.card` 打开能力。

## 被新方案取代的原因

早期方案只覆盖本地上传器侧资源外置和处理后 `.card` 提交，没有完整覆盖：

- 社区服务器数据模型；
- `.card` 主文件对象存储；
- `open-view` DTO；
- 前台 CardViewer source；
- CardViewer 远程 `.card` 渲染；
- 旧 `htmlUrl` / pipeline 降级；
- 测试与验收。

因此当前任务改以整体重构方案为准。
