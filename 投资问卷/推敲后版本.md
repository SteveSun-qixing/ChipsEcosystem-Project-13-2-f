# 请描述一下你的项目，具体是做什么的？

薯片生态先做 `.card` 卡片文件格式，以及围绕它的编辑、阅读、管理和分享工具。

`.card` 像一个更通用的 Word/PPT 文件，也像一个可以离线保存的网页。它可以把文字、图片、视频、电子书、网页、待办、资源文件等内容，连同它们之间的结构一起保存到一个文件里。用户可以像发送图片或文档一样发送一整套内容，而不是把视频、截图、文字、链接和清单拆开分别发送。

第一阶段，我们服务高信息密度创作者、教程作者、AI 工具重度用户和资料整理者，帮他们把复杂内容组织成一个可保存、可打开、可分享、可继续编辑的卡片文件。

长期看，薯片生态会围绕 `.card` 扩展成一个插件化软件生态。用户只安装一个薯片主机，各类播放器、阅读器、编辑器、查看器和内容社区都可以作为插件运行，共享统一的文件格式、运行时、主题、组件和权限系统。我们的目标是让个人内容资产不再锁死在单个软件里，而是能够长期保存、自由流转和跨场景消费。

## 你们正在研发或使用什么样的技术？

我们正在研发两层核心技术。

第一层是 `.card` 卡片文件格式。它本质上是一个采用 ZIP 存储模式打包的开放文件，内部包含元数据、结构文件、基础卡片配置和资源文件。它可以保存文本、图片、视频、音乐、电子书、网页、待办等不同内容，也能保存这些内容之间的结构。用户拿到一个 `.card` 文件后，可以像打开 Word/PPT 一样打开一套完整内容。

第二层是插件化 Host 架构。用户只安装一个薯片主机，卡片查看器、编辑器、播放器、阅读器、内容工具等都作为插件运行。插件通过 Bridge API 和 SDK 访问系统能力，不能直接绕过 Host 操作系统能力。这样可以让不同软件共享同一套文件格式、主题系统、组件库、权限系统和运行时。

当前主要技术栈是 TypeScript、React、Electron、Node.js、Fastify、PostgreSQL、Redis、S3/MinIO 和 ZIP 文件打包。我们也在探索 AI 辅助的软件迁移工作流，用来把优秀宽松开源项目改造成薯片生态插件。

## 你的用户是谁？典型用户场景是什么？你为用户解决什么问题？

第一阶段用户是高信息密度创作者和资料整理者，例如教程作者、技术博主、AI 工具重度用户、学生研究者和独立开发者。他们经常要把文字、图片、视频、网页、清单和资料文件组织在一起，再分享给别人或留给自己复用。

典型场景是：一个用户想分享一套教程，里面有 1 个视频、5 张手写笔记截图、1000 字说明、10 个步骤清单和若干参考资料。今天他通常只能把这些内容拆开：视频传网盘或平台，截图和文字发微信，清单放在待办软件，资料再做压缩包。接收者拿到的是一堆文件和链接，而不是一份完整内容。

`.card` 解决的是“复杂内容无法作为一个完整结构流通”的问题。创作者可以把这些材料按顺序组织成一张卡片文件，接收者像打开文档一样打开它，就能看到完整结构；如果想收藏、二次编辑或再次转发，也不需要重新拆分和组装。

长期看，普通用户也会受益，因为他们不用理解不同软件和文件格式的边界，只需要打开、保存和分享卡片。

## 这个项目的想法是从哪来的？为什么选择现在这个时间点来做？

这个想法来自我自己的长期创作经历。我做过漫画汉化、小说翻译、计算机教程、技术文章、资料整理和软件项目。AI 出现后，一个人的创作能力被明显放大，我也越来越频繁地同时处理文字、图片、视频、网页、代码和资料文件。

我一开始尝试用电子书管理器、图片素材管理器、视频管理器、笔记软件和个人网站来解决问题，但发现它们大多按文件类型或应用边界管理信息：图片归图片，视频归视频，笔记归笔记。即使某个软件能把内容组合起来，这个结构通常也锁在那个软件内部，迁移和再分发很麻烦。

我认为现在适合做，是因为 AI 正在让个人和小团队生产更多复杂、多模态内容。未来真正稀缺的不只是生成内容的能力，而是把一组内容组织成可理解、可保存、可复用、可传播结构的能力。

同时，Electron/Web 技术、开源生态和 AI 编程工具也让小团队有机会搭建过去很难完成的软件基础设施。几年前个人多模态内容生产还没有这么强，几年后新的内容工具可能会形成更多数据孤岛。现在从开放文件格式和创作者工具切入，是一个比较好的时间点。

长期看，我希望继续把这种统一体验扩展到内容生产、管理、分发和消费的完整链路。

## 你的项目有什么特别的地方？

薯片生态的特别之处在于，我们不是先做一个新的笔记软件或内容社区，而是先做一个可流通的结构化内容载体。

第一，`.card` 保存的不只是内容本身，还保存内容结构。文字、图片、视频、网页、清单和资源文件可以被组织成一份完整文件，而不是散落在不同应用里。

第二，它不是绑定在单一云端产品里的页面，而是一个开放文件格式。用户可以像保存 Word、PPT、PDF 一样保存、复制、发送和备份自己的内容资产。

第三，我们用插件化 Host 架构承载不同内容类型和软件能力。基础卡片、播放器、阅读器、编辑器、布局和主题都可以插件化扩展，未来可以逐步吸收优秀宽松开源项目，而不是所有功能都由主程序硬编码。

第四，我们的竞争路径不是一开始挑战大平台的内容分发，而是先从创作者本地工具和资料管理切入，积累文件格式、编辑体验和内容资产，再逐步扩展到社区和消费场景。

## 现在用户在使用什么替代方案或者竞品？

用户现在主要用四类替代方案。

第一类是笔记和知识库工具，例如 Notion、Obsidian、思源笔记、滴答清单等。它们适合记录和组织内容，但内容结构通常绑定在应用或工作区里，跨工具迁移和作为独立文件流通并不自然。

第二类是单类型素材管理工具，例如 Eagle、Billfish、VidHub、Infuse、Calibre 等。它们分别管理图片、视频、电子书等资源，但很难把多种类型内容组织成一份完整结构。

第三类是传统分发方式，例如 PDF、PPT、网页、压缩包、网盘链接。它们适合传播，但要么交互和结构表达有限，要么接收者拿到的是一堆文件。

第四类是最近一年随着 AI 编程出现的大量个性化信息管理工具。它们说明需求真实，但也带来新的孤岛：每个工具都有自己的数据结构和界面，用户很难在工具之间迁移。

薯片生态希望把“内容结构”沉淀到 `.card` 文件，把“软件能力”沉淀到插件生态，而不是每个需求都新造一个孤立应用。

## 在你的行业里，有什么大多数人都不同意的但你认为是对的观点？

我认为 AI 编程会让“生成软件”变得越来越便宜，但不会让大多数消费者长期使用大量完全个性化的小软件。

原因是普通用户真正想要的不是维护软件，而是稳定、好用、低心智负担地完成任务。在成熟软件领域，产品体验往往会逐渐收敛到少数高质量范式；AI 会提高供给速度，但不会消除用户对标准化、互操作和长期内容资产管理的需求。

所以我认为，AI 时代更大的机会不只是让每个人生成自己的软件，而是建立一种开放的内容格式和插件生态：个性化能力可以存在，但用户的内容结构和资产不应该被锁在某个一次性生成的应用里。
