# 你们正在研发或使用什么样的技术？

## 这题真正考察什么

这题不是让你展示所有技术栈，而是看你是否理解产品背后的技术壁垒和实现路径。技术描述应该服务于商业判断：为什么这件事你能做，为什么这套架构能支撑长期生态。

## 当前答案优点

当前答案有两层：`.card` 文件格式和类似微信小程序的 Host/插件架构。技术栈也比较清楚。

## 当前答案风险

“类似 Word 或 PPT，但可以保存更多类型的信息”是好比喻，但如果只讲这一句，评审会问：这和 Notion 导出、网页打包、PDF、EPUB、PPT 有什么不同？

需要强调三个技术点：

1. `.card` 是可流通的开放文件，而不是某个云端应用里的页面。
2. 卡片内容由基础卡片插件渲染，格式可扩展。
3. Host 统一承载插件，降低未来软件生态扩展成本。

## 推荐写法

我们正在研发两层核心技术。

第一层是 `.card` 卡片文件格式。它本质上是一个采用 ZIP 存储模式打包的开放文件，内部包含元数据、结构文件、基础卡片配置和资源文件。它可以保存文本、图片、视频、音乐、电子书、网页、待办等不同内容，也能保存这些内容之间的结构。用户拿到一个 `.card` 文件后，可以像打开 Word/PPT 一样打开一套完整内容。

第二层是插件化 Host 架构。用户只安装一个薯片主机，卡片查看器、编辑器、播放器、阅读器、内容工具等都作为插件运行。插件通过 Bridge API 和 SDK 访问系统能力，不能直接绕过 Host 操作系统能力。这样可以让不同软件共享同一套文件格式、主题系统、组件库、权限系统和运行时。

当前主要技术栈是 TypeScript、React、Electron、Node.js、Fastify、PostgreSQL、Redis、S3/MinIO 和 ZIP 文件打包。我们也在探索 AI 辅助的软件迁移工作流，用来把优秀宽松开源项目改造成薯片生态插件。

## 词句推敲

“系统底层”可以换成“插件化 Host 架构”，更具体。

“未来人们可以用很轻量的方式使用整个生态的各种软件”略抽象，建议用“用户只安装一个薯片主机，各类工具作为插件运行”。

“兼收并蓄进我们的生态”可以换成“改造成薯片生态插件”，更清晰。

## 注意边界

不要过度强调 AI 自动化开发工作流。它是亮点，但如果写太重，评审会误以为你的核心是 AI 代码迁移，而不是 `.card` 和内容生态。
