## 一、结论先行

薯片组件库对标 SwiftUI 已经历三轮开发（task022 框架化重构、task023 高级感、多轮工单修补），**架构方向正确但落地面临系统性断裂**。当前状态概括为 7 点：

1. **71 个契约、802 个 token、256 个测试、9 步质量门禁全绿——但建立在"虚假门禁"之上**：真实 `tsc --noEmit` 有 3886 个类型错误、lint 不跑 ESLint、性能门禁不测渲染、a11y 门禁不操作真实 DOM、quality:coverage 不是代码覆盖率。门禁绿 ≠ 组件可用。

2. **组件主实现是 16999 行单文件 JS**：无 TS 源码、无按组件拆分、无 tree-shaking，d.ts 手写且与实现清单不一致（缺 resolveSystemMessageQueue）。组件实现细节 38 项问题：`...rest` 被吞（6 个组件 className/onClick/aria 全丢）、loading 状态全局不可达、弹层全部内联渲染且点击外部不关闭、description/status 静态 id 串场、渲染期调用外部回调、window 事件监听器泄漏等。

3. **主题系统架构链路是通的，但"无头组件 + 主题注入"只通了架构、没通语义**：scope 三方 71/71 对齐、cpx 转换 4 入口全覆盖、契约门禁生效——但 loading 契约-主题-代码三方死链（契约 63 处声明、CSS 0 选择器、代码死分支）、布局组件 9 处焦点样式死区、28 个 status part 无样式（错误信息不可见）、menu/tooltip/popover 根节点无样式、Primitive 与 Chips* 双实现同 scope 串扰、16 个组件 focus-outline token 定义后无人消费；**暗色主题 dist 产物严重过期**（仅覆盖 33/71 scope，21 个 token 死引用）属发布级阻断。

4. **多语言系统"协议冻结、运行时未收口"**：三级词典加载链完全缺失（Host 词典只有硬编码 2 个 key）、translate 缺失 key 抛错（违反规范回退语义且与 SDK mock 不一致）、语言选择不持久化、组件库 16 处硬编码英文文案、组件默认 i18n key 在所有语言包中是死 key、复数/性别/RTL/格式化能力未实现、7 个应用逐字复制私有 formatMessage、EditingEngine 与 Host i18n 显式解耦。

5. **组件库覆盖了"基础控件"，没有覆盖"应用组合模式"**：9 个应用约 60 个私有组件逐一对照后——**完全缺失约 18 类**（媒体进度条变种/抽屉/分组列表/描述列表/活动栏/状态栏/文件拖放区/素材网格/预览窗格/工作台壳层/站点页头页脚/详情页等，task023"缺少的组件.md"18 项全部有真实私有实现佐证）、**近似变种缺失约 15 处**（滑块→媒体进度条、Dialog→抽屉、VirtualList→分组列表等，3 个播放器各自实现进度条、4 个应用 4 种图标按钮+tooltip）、**组件库已有但应用不用约 20 处**（CommunityClient 系统性绕开：重造对话框 239 行、自绘 14 图标）。

6. **8/9 个应用基本不消费组件库**：媒体三件套各只用 1 个 ChipsIcon；8 个应用共 189 个私有 token、约 780 处硬编码色值；CommunityClient 建了第二套完整主题系统（--ccps-* 65 token、--chips- token 使用数 = 0）；应用壳层 8/9 是私有 CSS；形成"组件库不好用→应用自造→组件库更没人用"的负循环。

7. **对标 SwiftUI 的本质错位**：SwiftUI 处理功能需求只有四种模式——M1 一等公民场景容器（List+Section/Form/Inspector/LabeledContent）、M2 Modifier 能力（.help/.overlay/.sheet/.dropDestination 挂在任意视图）、M3 组合原语（Slider/Canvas/Gesture 组合，不做专用组件）、M4 系统级封装（AVKit/PhotosPicker）。薯片组件库**只有 M1 的少量容器、完全没有 M2 能力层、M3 原语不完整**——这就是应用被迫自造的全部原因。用户已定调：**SwiftUI 怎么处理，我们就怎么处理**（详见分报告 08）。

**一句话总结**：组件之下没有可靠的工程基础（源码、类型、真实测试），组件之上没有应用组合模式（M2 能力层与壳层容器），旁边主题系统在状态语义层断链、多语言系统在运行时未收口，应用侧全部各造各的。五维同时缺位，导致"简单的面板都做不好"。

**特别说明（分报告 09）**：以上问题**不是没有规划**——task022（2026-05-21）的《薯片前端框架开发重构方案》已完整规划了单文件拆分、真实门禁、modifier 能力（9 项）、List/Table 容器、18 种组件状态、i18n key 体系、壳层组件与视觉回归。未贯彻的根因是：①执行只做了"增量加组件"没做"工程改造"；②技术栈决策（工单094）悬空从未做出；③2026-05-27"第一版冻结"把关键工作主动划出范围且后续无任务承接；④task023 被收窄为"只升级主题包"；⑤第一版冻结建立在名义门禁上，基线质量存疑。**第四次重构的起点是捡起这些规划资产，按 M1-M4 四模式重新编排，以"工程改造"方式执行。**

## 二、生态架构设计意图（对标基准）

### 2.1 分层定位（生态设计原稿/06、生态共用技术文档/架构设计/15）

| 层级 | 名称 | 核心职责 | 只允许依赖 | 禁止依赖 |
|---|---|---|---|---|
| L10 | Component Headless | 状态机、结构、a11y | Theme Runtime(接口) | 视觉硬编码 |
| L11 | Theme Runtime | token 解析、作用域覆盖、变量注入 | Theme Package | 业务逻辑 |
| L12 | App/Page Domain | 页面状态、业务流程、编排 | L7-L11 | L1-L5 细节 |

- 组件库只负责结构、状态机与 a11y，**零视觉硬编码**，视觉由主题包注入；
- 官方前端统一 React 技术栈；所有界面文案走多语言系统；所有视觉走主题系统与 token；
- 主题配置六级覆盖：`global -> app -> box -> composite-card -> base-card -> component`（component 权重最高）；
- 一个主题包只承载一种外观，暗色是独立 themeId 的正式主题包；
- 不做临时版、简化版、占位实现，不留 TODO；应用级组合应留在应用项目内，但不允许应用长期私造组件库应覆盖的能力。

### 2.2 对标 SwiftUI 的正式口径（生态共用技术文档/组件库/09-SwiftUI对标基础控件能力矩阵）

- 已收口基础控件矩阵（Text/Label/Icon 至 Image/Media/ErrorState 共 7 批）；
- 每一批必须同步组件库、contract、组件 token、默认主题、暗色主题、公共文档和测试；
- "已落地"= 公开导出 + data-scope/part/state + a11y 规则 + contract + token + 默认/暗色主题 + 测试全部接入；
- task022 差距分析明确：**对标目标是"薯片前端框架"，不是只对标组件清单**；需补 App/Scene/Window/Document、声明式 View 模型、状态环境、导航命令、预览、性能工具。
- **2026-08-06 用户定调（分报告 08）**：SwiftUI 怎么处理功能对组件的需要，我们就怎么处理——即采用 M1 容器 / M2 Modifier 能力 / M3 组合原语 / M4 系统级封装四模式，而不是"为每个应用场景发明专用组件"。

### 2.3 主题系统正式承诺（15-主题系统设计.md、01-主题包开发指南.md）

- 五层 token：ref → sys → motion/layout → comp 单向依赖；
- `dist/tokens.json` 为 Theme Runtime 唯一正式消费产物；
- cpx 进入浏览器环境统一按 1024 基准转 vw：`12cpx → 1.171875vw`；
- 契约门禁：官方主题包 contract 必须由组件库 contracts 等值生成，缺 required token 输出阻断级 `THEME_REQUIRED_TOKEN_MISSING`；
- 主题矩阵快照（preview/）供测试与设置面板复用；
- 图标：Material Symbols variable font 三套 @font-face 交付到 dist/icons/variablefont/。

### 2.4 多语言系统正式承诺（协议与接口标准/03-多语言规范.md）

- 固定动作：`i18n.getCurrent / setCurrent / translate / listLocales`（i18n.read / i18n.write 权限）；
- 三级加载链：插件词典 > 应用词典 > 生态词典；
- 缺失 key：告警 + 回退默认文案模板 + CI 门禁输出缺失 key 列表 + 缺失率超 5% 禁止发布；
- 渲染期同步文案必须用组件库同步 adapter（`useChipsI18nText` 等），查找顺序：当前 locale → fallbackLocales → fallbackLocale → defaultLocale → key；
- 语言切换必须走 Host `i18n.setCurrent`，不得改本地状态冒充切换成功。

## 五、根因分析

把 80 项主问题（90+ 子项）归拢，根因有五条：

1. **组件库从未建立"源码工程"**：组件直接以 16999 行单文件 JS 交付，没有 TS 源码、没有按组件拆分、没有构建产物验收、没有真实门禁（typecheck/lint/perf/a11y 全部是"名义门禁"）。代码不可审查、不可类型化，BUG 只能靠工单一个一个补——这解释了"各种 BUG、各种不稳定"。

2. **"无头组件 + 主题注入"链路只通了架构、没通语义**：scope 层对齐了（71/71），但状态语义（loading 遮蔽、focus 死区）、part 覆盖（28 个 status 无样式、menu/tooltip/popover 根无样式）、双实现串扰（Primitive vs Chips*）三处断链，导致组件在真实主题下"有结构没反馈、有状态没视觉"——这解释了"不美观"。

3. **多语言系统"协议冻结、运行时未收口"**：词典加载链、缺失 key 治理、语言持久化全是空的，组件库 16 处硬编码英文 + 死 key 体系，7 份重复 formatMessage——这解释了"体验细节粗糙"。

4. **组件库只有"整件组件"一个维度，没有 M2 能力层（modifier 等价物）**：SwiftUI 把 tooltip/遮罩/抽屉/拖放等做成挂在任意视图上的能力；薯片组件库只能"做组件"，应用需要的能力挂不上去，只能自造（4 个应用 4 种 tooltip、3 处拖放、3 处进度条、3 处对话框重造）。同时 M1 容器缺 List/Section/Form 等最常用的，M3 原语不完整——这是"应用被迫自造"的直接原因。

5. **应用侧无人真正使用组件库，形成负循环**：8/9 应用壳层私有 CSS、189 个私有 token、1 套第二主题系统、1 套显式解耦 i18n，形成"组件库不好用→应用自造→组件库更没人用→反馈更少"的负循环。task023 计划了壳层组件与治理，但只执行了主题包升级——**壳层组件（18 项）与视觉回归门禁是"高级感"的最后两块拼图，至今缺失**。

| i18n | 平台本地化 | 运行时未收口，组件级 key 死链 | 差距明显 |
| 动效 | Animation/Transition/Material | motion token 有，框架级动效 API 无 | 缺失 |
| 预览 | Xcode 实时预览 | 无等价预览体系（chipsdev preview 仅 gallery 矩阵） | 缺失 |
| 性能分析 | Instruments | perf 门禁不测渲染 | 名义存在 |

### 6.2 SwiftUI 处理功能需求的四种模式（分报告 08 核心，用户定调）

| 模式 | 是什么 | 例子 | 薯片现状 |
|---|---|---|---|
| **M1 一等公民场景容器** | 高频、跨应用、语义稳定 → 做成框架容器 | `List+Section`（分组列表）、`Form`、`NavigationSplitView`、`TabView`、`Inspector`、`LabeledContent`（键值行）、`GroupBox`、`DisclosureGroup`、`Gauge/ProgressView`、`Picker`、`Menu` | 有部分（NavigationSplitView/Tabs/Form/Inspector），**缺 List+Section/KeyValue/Sheet 等最常用的** |
| **M2 Modifier 能力** | 能力挂在"任意视图"上 → modifier 叠加 | `.help()`（tooltip）、`.overlay()`（遮罩）、`.sheet()/.popover()/.alert()`（呈现）、`.contextMenu()`、`.dropDestination()/.draggable()`（拖放）、`.badge()` | **完全没有**——这是应用自造的最大原因 |
| **M3 组合原语** | 特定场景复杂 UI → 框架只给原语（Slider/Canvas/Gesture/TimelineView），文档化组合 | 媒体进度条（Slider 定制 track）、活动栏、状态栏、无限画布、浮动窗口——SwiftUI 通通没有专用组件 | Slider 缺媒体变种（buffer/章节标记/hover 预览）；无 Canvas/Gesture 对应物；组合模式无文档 |
| **M4 系统级封装** | 平台级完整体验 → 系统提供整机 UI | AVKit `VideoPlayer`、`PhotosPicker` | 缺 Host 级系统组件（播放器壳层、资源选择器等） |

### 7.2 执行规则（分报告 08 第四节）

1. **不再为"应用场景"发明专用组件**——先判断属于 M1/M2/M3/M4 哪一类；M2 优先做成能力，M3 做成原语+文档化组合模式，M4 留给 Host；
2. **应用自造组件一律先对照分报告 07 映射表**：属于"有但不用"的 → 迁移到现有组件；属于"变种缺失"的 → 登记组件库增强；属于"完全缺失"的 → 按 M1/M2 清单补正式组件；业务特有 → 保留并登记边界；
3. **新组件必须同时交付**：契约（data-scope/part/state）+ 组件 token + 默认/暗色主题 CSS + 测试 + 文档（05-可访问性与质量基线、09-能力矩阵同步）；
4. **M2 能力层必须优先落地**：它是解决"应用自造"的最短路径；
5. 组件库第四次重构的验收标准 = 分报告 07 的缺口清单全部收口：18 项完全缺失 → 组件/能力；15 项变种 → 增强；20 项"有但不用" → 应用迁移完毕且新增门禁拦截。
