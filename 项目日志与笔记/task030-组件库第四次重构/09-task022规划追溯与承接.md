## 三、为什么没贯彻下去（5 个原因，附证据）

### 原因 1：执行只做了"增量加组件"，没有做"工程改造"

06 工单级任务 000-058 的执行形态：任务014（布局原语补齐）、015（基础控件 7 批）、016（Compound 迁移 8 批）、017（状态环境）、018（焦点 a11y）、019（测试工具）——全部是**给 16999 行 index.js 加代码、加 contract 文件、加脚本**；而规划中"拆分 index.js、组件独立目录、direct import、真实门禁"属于**改造**，在执行中全部被跳过或做成名义实现（run-typecheck.mjs 就是 `node --check`）。工作日志里任务019 的产出是"run-tests/run-a11y/run-perf 等脚本"，但脚本内容都是轻量检查。

### 原因 2：技术栈决策（工单094 P0 第一项）从未做出，架构收口悬空

04-01 §5.1 P0 第 1 条与 §11 风险第 1 条都要求"在 Ark/Zag/Tamagui 与自研状态机之间做正式路线决策"。该决策从未做出：工单094 2026-05-21 登记 → 2026-08-02 复核"缺口仍存在，待处理"；期间组件继续以自研状态机加码，文档继续宣称 Ark/Tamagui。**决策悬空导致"是否重构实现"永远无法开始**。

### 原因 3：2026-05-27"第一版冻结"主动把关键工作划出范围

任务058.05 明确"第一版不包含：高级视觉产品化（工单114）、chipsdev build 主题分流（工单111）、任务059 技能、更多主题、Web Host Shell、开放项目深度同化"；后续路线第 2 条把"视觉产品化"整体推向工单114。而工单114 至今"处理中"——**058.05 写的后续路线没有任务承接**（task023 只做了一半就停了）。

### 原因 4：task023（高级感）被收窄为"只升级主题包 + 只替换已有组件"

task023 2026-05-26 收窄口径："组件库没有的组件先不替换，只登记到缺少的组件.md"——结果 P2 壳层组件（ActivityBar/StatusBar/PropertyGrid 等）从未进入组件库，只留下 18 项登记清单；视觉回归门禁从未建立；工单114 挂着"处理中"。

### 原因 5：第一版冻结的"质量门禁"本身是名义门禁，冻结基线质量存疑

058.05 §7 记录"ComponentLibrary `npm run verify` 与 `quality:gate` 在任务057、058.03通过"——但这些门禁就是 node --check 型名义门禁（3886 个真实 tsc 错误全绿）。**"自动化条件发布"发布在一个虚假质量基线上**，后续所有工作都在这个基线上叠加，问题越积越多。

### 补充事实

- 任务059（生态全类型开发技能 vNext）被用户明确取消（2026-05-26），不进入路线；
- 任务051（旧应用市场）取消，社区平台重新设计；
- task022 收尾时工作区仍有 132 条未提交状态（设置面板/主题包/编辑引擎 WIP、task023 资料、新工单115 等）——"自动化条件发布"结论是带 WIP 的。
